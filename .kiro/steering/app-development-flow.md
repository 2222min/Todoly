# 🚀 AI 앱 개발 방법론 — 자동 실행 플로우

이 steering은 항상 활성화되어 있으며, 앱 개발/변경 관련 모든 요청에 자동으로 적용됩니다.

---

## 트리거 조건

사용자가 아래와 같은 의도를 표현하면 이 플로우를 시작합니다:
- "~앱 만들고 싶어", "~앱 만들자", "~앱 개발하자"
- "이런 아이디어가 있는데", "이런 서비스 어때?"
- 앱/서비스 아이디어를 설명하는 메시지

플로우 시작 전 반드시 사용자에게 확인합니다:
> "앱 개발 플로우를 시작할게요. 9단계(기획→리뷰→확정→디자인→디자인리뷰→디자인확정→개발스펙→개발가이드→구현)를 순서대로 진행합니다. 각 단계마다 결과를 보여드리고 확인받은 후 다음 단계로 넘어갈게요. 시작할까요?"

사용자가 긍정하면(네, 좋아, ㅇㅇ, 고고, 시작 등) 1단계부터 실행합니다.

---

## 플로우 실행 규칙

### 공통 규칙
1. 각 단계의 산출물은 반드시 파일로 저장합니다
2. 각 단계 완료 후 사용자에게 결과를 요약하고 확인을 받습니다
3. 사용자가 수정을 요청하면 해당 단계에서 수정 후 다시 확인받습니다
4. 사용자가 "다음", "넘어가자", "OK" 등 긍정하면 다음 단계로 진행합니다
5. 사용자가 "건너뛰자", "스킵" 등을 말하면 해당 단계를 건너뜁니다

### 비용 최소화 원칙 (모든 단계에 적용)
- 서버 인프라 비용 월 $0 목표 (무료 티어 우선)
- 직접 구현보다 매니지드 서비스/BaaS 우선
- v1은 핵심 기능만. 나머지는 향후 업데이트로 분리
- 1인 개발 기준으로 설계

### 코드 품질 원칙 (7~9단계, 코드 생성 시 반드시 적용)

아래 원칙은 코드를 생성하거나 리뷰할 때 항상 지켜야 합니다. 위반하는 코드를 작성하지 않습니다.

#### 1. 순수 함수 (Pure Functions)
- 같은 입력에는 항상 같은 출력을 반환한다
- 함수 외부 상태를 변경하지 않는다 (부수 효과 없음)
- 부수 효과가 필요한 경우(네트워크, DB, UI 업데이트), 순수 로직과 부수 효과를 분리한다
- 비즈니스 로직은 반드시 순수 함수로 작성한다

```
✅ 좋은 예: 필터링 로직을 순수 함수로 분리
func filterActiveTodos(todos: [Todo]) -> [Todo] {
    return todos.filter { !$0.isCompleted && !$0.isDeleted }
}

❌ 나쁜 예: 필터링하면서 외부 상태를 변경
func filterActiveTodos() {
    self.filteredList = self.allTodos.filter { ... }
    self.updateUI()  // 부수 효과 섞임
}
```

#### 2. 모듈화 (Modularization)
- 기능 단위로 파일/모듈을 분리한다
- 한 파일이 300줄을 넘으면 분리를 검토한다
- 모듈 간 의존성은 최소화한다 (느슨한 결합)
- 공통 유틸리티는 별도 모듈로 추출한다

```
✅ 좋은 예: 레이어 + 기능별 분리
Domain/Logic/TodoMutationLogic.swift   ← Todo 상태 변환만
Domain/Logic/TodoFilterLogic.swift     ← Todo 필터링만
Data/Services/NotificationService.swift ← 알림만
Features/Calendar/CalendarView.swift   ← 캘린더 화면만

❌ 나쁜 예: 하나에 다 넣기
Services/AppService.swift        ← 인증+DB+알림+기타 전부
TodoStore.swift                  ← 비즈니스 로직+필터링+상태관리+알림 전부
```

#### 3. 단일 책임 원칙 (Single Responsibility)
- 하나의 함수는 하나의 일만 한다
- 하나의 클래스/구조체는 하나의 역할만 한다
- 함수 이름만 보고 무슨 일을 하는지 알 수 있어야 한다
- "그리고(and)"가 들어가는 함수명은 분리 대상이다

```
✅ 좋은 예:
func validateTitle(_ title: String) -> Bool
func saveTodo(_ todo: Todo) async throws
func sendNotification(for todo: Todo)

❌ 나쁜 예:
func validateAndSaveTodoAndNotify(_ title: String)
```

#### 4. SOLID 원칙

**S — Single Responsibility (위 3번과 동일)**

**O — Open/Closed (개방/폐쇄)**
- 확장에는 열려있고, 수정에는 닫혀있게 설계한다
- 새 기능 추가 시 기존 코드를 수정하지 않고 확장할 수 있어야 한다
- Protocol/Interface를 활용한다

**L — Liskov Substitution (리스코프 치환)**
- 하위 타입은 상위 타입을 대체할 수 있어야 한다
- Protocol을 구현할 때 계약을 위반하지 않는다

**I — Interface Segregation (인터페이스 분리)**
- 큰 인터페이스보다 작고 구체적인 인터페이스 여러 개가 낫다
- 사용하지 않는 메서드에 의존하지 않는다

```
✅ 좋은 예:
protocol Readable { func fetch() async throws -> [Todo] }
protocol Writable { func save(_ todo: Todo) async throws }
protocol Deletable { func delete(_ id: String) async throws }

❌ 나쁜 예:
protocol DataService {
    func fetch() async throws -> [Todo]
    func save(_ todo: Todo) async throws
    func delete(_ id: String) async throws
    func syncOffline() async throws
    func clearCache()
    func exportCSV() -> Data
}
```

**D — Dependency Inversion (의존성 역전)**
- 구체 구현이 아닌 추상(Protocol)에 의존한다
- ViewModel은 Service의 Protocol에 의존하고, 구체 구현은 주입받는다

```
✅ 좋은 예:
class TodoListViewModel {
    private let todoService: TodoServiceProtocol  // 추상에 의존
    init(todoService: TodoServiceProtocol) { ... }
}

❌ 나쁜 예:
class TodoListViewModel {
    private let service = FirestoreService()  // 구체 구현에 직접 의존
}
```

## 2단계: 기획 리뷰 (AI 멀티 페르소나)

### 실행
v1 기획안을 3가지 전문가 관점에서 리뷰합니다.

### 리뷰 관점
1. 사용성(Usability) 전문가
   - 사용자 플로우에 불편한 점
   - 단계가 너무 많은 기능
   - 인라인 추가 등 빠른 경로 제안

2. 가시성(Visibility) 전문가
   - 중요 정보의 시각적 강조
   - 우선순위/마감일 등의 시각화 방안
   - 빈 상태(Empty State) 처리

3. 가독성(Readability) 전문가
   - 정보 밀도 적절성
   - 1차/2차 정보 계층 구조
   - 완료 항목 처리 방식

### 분류
- 🔴 반드시 수정 (Critical)
- 🟡 권장 수정 (Recommended)

### 산출물
```
docs/planning/v1_리뷰.md
```

### 사용자 확인
> "리뷰 결과입니다. 🔴 N건, 🟡 N건이 나왔어요. 확인 후 다음 단계(피드백 반영)로 넘어갈까요?"

## 7단계: 개발 스펙 논의

### 실행
개발 스펙을 논의합니다. 비용 최소화가 핵심입니다.

### AI 역할
1. 시니어 개발자 (아키텍처) — 기술 스택, 비용 최적화
2. 서버 개발자 — 서버리스 vs BaaS, 무료 티어 분석

### 포함 내용
- 기술 스택 확정 (항목 | 결정 | 이유)
- 데이터 구조 (NoSQL/SQL 설계)
- 프로젝트 폴더 구조
- 구현 순서 (우선순위별)
- 예상 일정
- 비용 비교 (기존 방식 vs 경량화)
- 아키텍처 설계 시 코드 품질 원칙(순수 함수, 모듈화, 단일 책임, SOLID) 반영
  - Protocol 정의 목록 (어떤 서비스를 추상화할지)
  - 순수 로직 vs 부수 효과 분리 구조
  - 폴더 구조에 모듈 경계 반영

### 비용 최소화 체크리스트
| 항목 | 선택지 |

| 서버 | Firebase Spark / Supabase Free / Cloudflare Workers Free |

| DB | Firestore / Supabase PostgreSQL |
| 푸시 알림 | 로컬 알림 먼저 → 서버 푸시는 나중에 |
| 호스팅 | Vercel Free / Netlify Free |

## 9단계: 구현

### 실행
문서를 기반으로 코드를 생성합니다.

### 구현 순서
1. 프로젝트 셋업 (폴더 구조, 의존성)
2. 데이터 모델 정의 (`Domain/Models/`)
3. 순수 비즈니스 로직 (`Domain/Logic/` — 순수 함수)
4. Protocol 정의 (`Domain/Protocols/`)
5. 핵심 서비스 구현 (`Data/Services/` — Protocol 구현)
6. Store 구현 (`Data/Store/` — 순수 로직 호출 → 결과 적용)
7. 메인 화면 UI (`Features/`)
8. 상세/부가 화면 UI
9. 공통 UI 컴포넌트 (`Core/Components/`)
10. 통합 점검

> **참고**: 프로젝트 아키텍처 상세는 `project-architecture.md` 스티어링을 참조합니다.
> 코드 품질 규칙은 `code-quality-rules.md` 스티어링을 참조합니다.

### 구현 중 리뷰
각 화면/기능 구현 후 자체 리뷰를 수행합니다:
- 기획안과 일치하는가
- 성능 이슈는 없는가
- 접근성은 충족하는가
- 에러 처리는 적절한가
- **순수 함수**: 비즈니스 로직이 부수 효과와 분리되어 있는가
- **모듈화**: 파일이 300줄을 넘지 않고, 기능별로 분리되어 있는가
- **단일 책임**: 각 함수/클래스가 하나의 역할만 하는가
- **SOLID**: Protocol 기반 추상화, 의존성 주입이 적용되어 있는가

위 코드 품질 원칙을 위반하는 코드가 발견되면, 다음 단계로 넘어가기 전에 리팩토링합니다.

### 각 구현 항목 완료 시

## 🔴 변경 관리 프로세스 (필수)

**핵심 규칙: 코드를 직접 수정하지 않는다. 반드시 문서부터 업데이트한다.**

사용자가 아래와 같은 요청을 하면 변경 관리 프로세스를 실행합니다:
- "이 기능 바꿔줘", "이거 수정해줘", "이것도 추가해줘"
- "이 화면 좀 다르게 해줘", "이 동작 변경해줘"
- "새로운 기능 넣어줘", "이거 빼줘"
- 기획/디자인/기능에 대한 모든 변경 요청

### 절대 하지 않는 것
- ❌ 변경 요청을 받자마자 바로 코드 수정
- ❌ 문서 업데이트 없이 코드만 변경
- ❌ 영향 범위 파악 없이 한 파일만 수정

### 변경 프로세스 5단계

#### Step 1. 변경 요청 분석
사용자의 요청을 분석하고 분류합니다.

| 변경 유형 | 예시 | 영향 범위 |
|----------|------|----------|
| 기능 추가 | "알림 기능 넣어줘" | 기획 → 디자인 → 스펙 → 코드 |
| 기능 수정 | "삭제를 스와이프 말고 버튼으로" | 기획 → 디자인 → 코드 |
| 기능 삭제 | "카테고리 기능 빼자" | 기획 → 디자인 → 스펙 → 코드 |
| UI 변경 | "이 화면 레이아웃 바꿔줘" | 디자인 → 코드 |
| 버그 수정 | "이거 동작이 이상해" | 코드 (기획 확인 후) |
| 데이터 변경 | "필드 추가해줘" | 기획 → 스펙 → 코드 |

사용자에게 분석 결과를 알려줍니다:
> "변경 요청을 분석했어요.
> - 유형: [기능 추가/수정/삭제/UI 변경/버그 수정]
> - 영향 범위: [기획 → 디자인 → 스펙 → 코드]
> - 수정 대상 문서: [목록]
> - 수정 대상 코드: [목록]
> 진행할까요?"

#### Step 2. 기획 문서 업데이트
영향 범위에 기획이 포함되면:
1. `docs/planning/FINAL_기획안.md`를 업데이트합니다
2. 변경 이력을 문서 하단 승인 이력 테이블에 추가합니다
3. 변경된 부분에 `(변경: YYYY-MM-DD)` 마크를 남깁니다

#### Step 3. 디자인 문서 업데이트
영향 범위에 디자인이 포함되면:
1. 관련 디자인 문서를 업데이트합니다
2. **Figma 디자인을 반드시 업데이트합니다** (figma-design-sync.md 스티어링 참조)
   - 새 화면 추가 시 → Figma에 해당 화면 생성
   - 기존 화면 변경 시 → Figma에서 해당 화면 수정
   - Figma 업데이트 없이 다음 단계로 넘어가지 않습니다
3. 디자인 리뷰(5단계)를 AI 멀티 페르소나로 자체 수행합니다
4. 디자인 확정(6단계)에서 리뷰 피드백을 Figma에 반영합니다

#### Step 4. 개발 스펙/가이드 업데이트
영향 범위에 스펙이 포함되면:
1. `docs/dev/개발스펙_논의록.md`를 업데이트합니다
2. 데이터 모델 변경이 있으면 마이그레이션 방안을 명시합니다
3. 관련 개발 가이드(텍스트 처리 등)를 업데이트합니다

#### Step 5. 코드 수정
문서 업데이트가 모두 완료된 후에만 코드를 수정합니다.
1. 업데이트된 문서를 기반으로 코드 수정
2. 코드 품질 4원칙(순수 함수, 모듈화, 단일 책임, SOLID) 준수
3. 수정 후 자체 리뷰 수행
4. 영향받는 다른 파일도 함께 수정 (연쇄 영향 확인)

### 변경 완료 후 보고
> "변경 완료했어요.
> - 수정된 문서: [목록]
> - 수정된 코드: [목록]
> - 확인 필요 사항: [있으면 명시]"

### 버그 수정의 경우 (예외 경로)
버그는 기획 의도와 코드 동작이 다른 것이므로:
1. 먼저 기획안을 확인해서 의도된 동작을 파악합니다
2. 기획 의도대로 동작하지 않는 것이면 → 코드만 수정 (문서는 이미 맞으므로)
3. 기획 자체가 잘못된 것이면 → 기획 문서부터 수정 후 코드 수정

## 🔴 절대 규칙 (위반 금지)

### 1. 단계 건너뛰기 금지
- 기획 → 리뷰 → 확정 → 디자인 → 디자인리뷰 → 디자인확정 → 개발스펙 → 개발가이드 → 구현
- 이 순서를 반드시 지킨다. 사용자가 명시적으로 "건너뛰자"라고 말하지 않는 한 단계를 생략하지 않는다
- 특히 **디자인 리뷰(5단계)와 디자인 확정(6단계)을 절대 건너뛰지 않는다**

### 2. AI 자체 수행 원칙
- PO 제안, 대표 리뷰, 디자인 리뷰 등 모든 멀티 페르소나 프로세스는 **AI가 자체적으로 수행**한다
- 사용자에게 "확인해주세요", "괜찮으면 넘어갈까요?" 등으로 대표 리뷰를 사용자에게 떠넘기지 않는다
- PO가 제안 → 대표가 리뷰 → 결과를 사용자에게 보고하는 구조이다
- 사용자는 최종 결과를 확인하고 추가 피드백을 줄 수 있지만, 리뷰 자체는 AI가 한다

### 3. Figma 동기화 필수
- UI/디자인 변경이 포함된 모든 작업에서 Figma 업데이트를 반드시 수행한다
- "코드 구현으로 넘어갈까요?"라고 묻기 전에 Figma가 최신 상태인지 확인한다
- Figma 업데이트 후 디자인 리뷰(5단계)를 거쳐야 코드 구현으로 넘어갈 수 있다

### 4. 변경 관리 시 전체 플로우 적용
- 기능 추가/수정 요청 시 변경 관리 프로세스 5단계를 모두 수행한다
- 영향 범위에 디자인이 포함되면 반드시 4→5→6단계(디자인→리뷰→확정)를 거친다
- 코드 수정(Step 5)은 문서 + Figma + 리뷰가 모두 완료된 후에만 진행한다
