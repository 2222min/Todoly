# 🚀 AI 앱 개발 방법론 — 자동 실행 플로우

이 steering은 항상 활성화되어 있으며, 앱 개발/변경 관련 모든 요청에 자동으로 적용됩니다.

---

## 트리거 조건

사용자가 아래와 같은 의도를 표현하면 이 플로우를 시작합니다:
- "~앱 만들고 싶어", "~앱 만들자", "~앱 개발하자"
- "이런 아이디어가 있는데", "이런 서비스 어때?"
- 앱/서비스 아이디어를 설명하는 메시지

플로우 시작 전 반드시 사용자에게 확인합니다:
> "앱 개발 플로우를 시작할게요. 9단계(기획→리뷰→확정→디자인→디자인리뷰→디자인확정→개발스펙→개발가이드→구현)를 순서대로 진행합니다. 각 단계마다 결과를 보여드리고 확인받은 후 다음 단계로 넘어갈게요. 시작할까요?"

사용자가 긍정하면(네, 좋아, ㅇㅇ, 고고, 시작 등) 1단계부터 실행합니다.

---

## 플로우 실행 규칙

### 공통 규칙
1. 각 단계의 산출물은 반드시 파일로 저장합니다
2. 각 단계 완료 후 사용자에게 결과를 요약하고 확인을 받습니다
3. 사용자가 수정을 요청하면 해당 단계에서 수정 후 다시 확인받습니다
4. 사용자가 "다음", "넘어가자", "OK" 등 긍정하면 다음 단계로 진행합니다
5. 사용자가 "건너뛰자", "스킵" 등을 말하면 해당 단계를 건너뜁니다

### 비용 최소화 원칙 (모든 단계에 적용)
- 서버 인프라 비용 월 $0 목표 (무료 티어 우선)
- 직접 구현보다 매니지드 서비스/BaaS 우선
- v1은 핵심 기능만. 나머지는 향후 업데이트로 분리
- 1인 개발 기준으로 설계

### 코드 품질 원칙 (7~9단계, 코드 생성 시 반드시 적용)

아래 원칙은 코드를 생성하거나 리뷰할 때 항상 지켜야 합니다.

#### 1. 순수 함수 (Pure Functions)
- 같은 입력에는 항상 같은 출력을 반환한다
- 함수 외부 상태를 변경하지 않는다 (부수 효과 없음)
- 부수 효과가 필요한 경우, 순수 로직과 부수 효과를 분리한다
- 비즈니스 로직은 반드시 순수 함수로 작성한다

#### 2. 모듈화 (Modularization)
- 기능 단위로 파일/모듈을 분리한다
- 한 파일이 300줄을 넘으면 분리를 검토한다
- 모듈 간 의존성은 최소화한다 (느슨한 결합)

#### 3. 단일 책임 원칙 (Single Responsibility)
- 하나의 함수는 하나의 일만 한다
- 하나의 클래스/구조체는 하나의 역할만 한다
- "그리고(and)"가 들어가는 함수명은 분리 대상이다

#### 4. SOLID 원칙
- 구체 구현이 아닌 추상(Protocol/Interface)에 의존한다
- 확장에는 열려있고, 수정에는 닫혀있게 설계한다
- 큰 인터페이스보다 작고 구체적인 인터페이스 여러 개가 낫다

## 1단계: 기획 초안 작성

### 실행
사용자의 아이디어를 기반으로 기획안 초안을 작성합니다.

### 포함 내용
1. 프로젝트 개요 (앱 이름 제안, 비전 한 줄, 타겟 유저)
2. 핵심 기능 정의 (기능별 테이블: 기능 | 설명 | 동작)
   - v1 필수 기능과 향후 업데이트 기능을 명확히 구분
3. 화면 구성 (각 화면 ASCII 와이어프레임 + 화면 간 이동 플로우)
4. 기술 요구사항
   - 클라이언트: 플랫폼, 언어, 프레임워크
   - 서버: 비용 $0 방안 우선 제안 (Firebase/Supabase 등)
   - 데이터 모델: 테이블 형태 (필드 | 타입 | 설명)
5. 비기능 요구사항 (성능, 오프라인, 다크모드, 접근성)

### 산출물
```
docs/planning/v1_기획안.md
```

### 사용자 확인
> "기획안 초안을 작성했어요. 확인해보시고, 수정할 부분이 있으면 말씀해주세요. 괜찮으면 다음 단계(기획 리뷰)로 넘어갈게요."

---

## 2단계: 기획 리뷰 (AI 멀티 페르소나)

### 실행
v1 기획안을 3가지 전문가 관점에서 리뷰합니다.

### 리뷰 관점
1. 사용성(Usability) 전문가 — 사용자 플로우, 빠른 경로 제안
2. 가시성(Visibility) 전문가 — 시각적 강조, 빈 상태 처리
3. 가독성(Readability) 전문가 — 정보 밀도, 계층 구조

### 분류
- 🔴 반드시 수정 (Critical)
- 🟡 권장 수정 (Recommended)

### 산출물
```
docs/planning/v1_리뷰.md
```

---

## 3단계: 기획 확정

### 실행
1. v1 리뷰의 🔴 항목 전부 반영
2. 🟡 항목 중 타당한 것 반영
3. 변경사항 상단에 요약
4. v2 기획안 작성 후, v1 피드백이 모두 반영되었는지 자체 검증
5. 최종 기획안(FINAL) 확정

### 산출물
```
docs/planning/v2_기획안.md
docs/planning/FINAL_기획안.md
```

### 사용자 확인
> "최종 기획안을 확정했어요. 다음은 디자인 단계인데, 세 가지 선택지가 있어요:
> A) Figma 디자인 (Figma MCP 연동)
> B) 코드로 바로 UI 구현 (디자인 건너뛰기)
> C) 디자인 + 리뷰 전체 플로우
> 어떻게 할까요?"

## 4단계: 디자인

### 실행 (사용자 선택에 따라)
**A) Figma 연동**: Figma MCP 도구로 디자인 생성

**C) 전체 플로우**: 디자인 가이드 문서 작성 후 Figma 작업

### 산출물 (A, C의 경우)
```

```

## 5단계: 디자인 리뷰 (AI 멀티 페르소나)

### 리뷰 관점
1. UI/비주얼 전문가 (시니어 8년차) — 시각적 완성도, 컬러, 타이포
2. UX/인터랙션 전문가 (시니어 7년차) — 플로우, 터치 타겟, 인터랙션
3. 일관성/접근성 전문가 (미들 4년차) — 폰트/색상 일관성, WCAG
4. 기획 정합성 전문가 (미들 3년차) — 기획안 대비 누락/추가 확인

### 역방향 피드백
디자인 과정에서 기획에 누락된 화면/기능을 발견하면 FINAL 기획안에 추가

### 산출물
```

docs/design/design_revision_guide.md
```

## 7단계: 개발 스펙 논의

### AI 역할
1. 시니어 개발자 (아키텍처) — 기술 스택, 비용 최적화
2. 서버 개발자 — 서버리스 vs BaaS, 무료 티어 분석

### 포함 내용
- 기술 스택 확정 (항목 | 결정 | 이유)
- 데이터 구조 (NoSQL/SQL 설계)
- 프로젝트 폴더 구조
- 구현 순서 (우선순위별)
- 예상 일정
- 비용 비교 (기존 방식 vs 경량화)
- 아키텍처 설계 시 코드 품질 원칙 반영

### 비용 최소화 체크리스트
| 항목 | 선택지 |
|------|--------|
| 서버 | Firebase Spark / Supabase Free / Cloudflare Workers Free |
| 인증 | Firebase Auth / Supabase Auth |
| DB | Firestore / Supabase PostgreSQL |
| 푸시 알림 | 로컬 알림 먼저 → 서버 푸시는 나중에 |
| 호스팅 | Vercel Free / Netlify Free |

### 산출물

## 9단계: 구현

### 구현 순서
1. 프로젝트 셋업 (폴더 구조, 의존성)
2. 데이터 모델 정의
3. 순수 비즈니스 로직 (순수 함수)
4. Protocol/Interface 정의
5. 핵심 서비스 구현 (Protocol 구현)
6. Store/상태 관리 구현 (순수 로직 호출 → 결과 적용)
7. 메인 화면 UI
8. 상세/부가 화면 UI
9. 공통 UI 컴포넌트
10. 통합 점검

### 구현 중 자체 리뷰
각 화면/기능 구현 후:
- 기획안과 일치하는가
- 성능 이슈는 없는가
- 접근성은 충족하는가
- 에러 처리는 적절한가
- 코드 품질 4원칙(순수 함수, 모듈화, 단일 책임, SOLID) 준수하는가

## 🔴 변경 관리 프로세스 (필수)

**핵심 규칙: 코드를 직접 수정하지 않는다. 반드시 문서부터 업데이트한다.**

### 변경 프로세스 5단계

#### Step 1. 변경 요청 분석
| 변경 유형 | 영향 범위 |
|----------|----------|
| 기능 추가 | 기획 → 디자인 → 스펙 → 코드 |
| 기능 수정 | 기획 → 디자인 → 코드 |
| 기능 삭제 | 기획 → 디자인 → 스펙 → 코드 |
| UI 변경 | 디자인 → 코드 |
| 버그 수정 | 코드 (기획 확인 후) |

#### Step 2. 기획 문서 업데이트
#### Step 3. 디자인 문서 업데이트
#### Step 4. 개발 스펙/가이드 업데이트
#### Step 5. 코드 수정 (문서 업데이트 완료 후에만)

### 버그 수정의 경우 (예외 경로)
1. 기획안 확인 → 의도된 동작 파악
2. 기획 의도대로 동작하지 않으면 → 코드만 수정
3. 기획 자체가 잘못이면 → 기획 문서부터 수정
