# 🚀 AI와 함께하는 앱 개발 방법론 가이드

> **"혼자서도, AI와 함께라면 팀처럼 만들 수 있다"**
>
> Claude, Codex, Cursor, Copilot 등 어떤 AI 코딩 도구를 쓰든 적용 가능한
> 체계적인 앱 개발 프로세스입니다.

---

## ⚡ 지금 바로 시작하기

### 방법 1: Kiro 사용자 (가장 쉬움)

Kiro를 쓰고 있다면, 채팅창에 `#app-development-flow`를 입력한 뒤 아이디어만 말하면 됩니다.

```
#app-development-flow

직장인을 위한 심플한 TODO 앱 만들고 싶어
```

AI가 "앱 개발 플로우를 시작할게요"라고 물어보면 "ㅇㅇ"이라고 답하세요.
그러면 9단계를 자동으로 진행하면서, 매 단계마다 확인을 받고 다음으로 넘어갑니다.

> steering 파일 위치: `.kiro/steering/app-development-flow.md`

### 방법 2: Claude / ChatGPT / Cursor 등 다른 도구

`.kiro/steering/app-development-flow.md` 파일의 내용을 복사해서
시스템 프롬프트(Custom Instructions / Rules for AI)에 붙여넣으세요.
그 다음 아이디어만 말하면 동일하게 자동 플로우가 실행됩니다.

| 도구 | 어디에 붙여넣나 |
|------|----------------|
| Claude (Web) | Project → Custom Instructions |
| ChatGPT | Settings → Custom Instructions 또는 GPTs |
| Cursor | `.cursorrules` 파일 또는 Rules for AI |
| Copilot | `.github/copilot-instructions.md` |
| Windsurf | `.windsurfrules` 파일 |
| Codex (CLI) | `AGENTS.md` 파일 |

### 방법 3: 수동으로 단계별 진행 (도구 무관)

시스템 프롬프트 설정 없이, 프롬프트를 하나씩 복붙하면서 진행하는 방법입니다.

#### 준비물
- AI 도구 아무거나 1개
- 만들고 싶은 앱 아이디어 1개 (한 줄이면 충분)

#### Step 1. 아래 프롬프트를 복사해서 AI에게 보내세요

```
나는 앱을 하나 만들려고 해.

[여기에 아이디어를 한두 줄로 적어줘. 예시:]
- "직장인을 위한 심플한 TODO 앱"
- "반려동물 산책 기록 앱"
- "동네 맛집 공유 앱"
- "개인 가계부 앱"

이 아이디어를 기반으로 기획안 초안을 작성해줘.
아래 형식을 따라줘:

## 1. 프로젝트 개요
- 앱 이름 (제안해줘)
- 비전 (한 줄)
- 타겟 유저

## 2. 핵심 기능 정의
- 각 기능별로 테이블 형태 (기능 | 설명 | 동작)
- v1 필수 기능과 향후 업데이트 기능을 구분해줘

## 3. 화면 구성
- 각 화면을 ASCII 와이어프레임으로 그려줘
- 화면 간 이동 플로우도 설명해줘

## 4. 기술 요구사항
- 클라이언트: 플랫폼, 언어, 프레임워크
- 서버: 💰 비용 $0으로 시작할 수 있는 방법 우선 제안
- 데이터 모델: 테이블 형태 (필드 | 타입 | 설명)

## 5. 비기능 요구사항
- 성능, 오프라인 지원, 다크모드, 접근성 등

결과물을 docs/planning/v1_기획안.md 파일로 저장해줘.
```

### Step 2. AI가 기획안을 만들어주면, 바로 이어서 이걸 보내세요

```
방금 만든 기획안을 리뷰해줘.
다음 3가지 관점에서 각각 피드백을 줘:

1. 사용성(Usability) 전문가로서
   - 사용자 플로우에 불편한 점은?
   - 단계가 너무 많은 기능은?

2. 가시성(Visibility) 전문가로서
   - 중요한 정보가 눈에 잘 띄는가?
   - 시각적 강조가 부족한 부분은?

3. 가독성(Readability) 전문가로서
   - 정보 밀도가 적절한가?
   - 한 화면에 너무 많은 정보를 담고 있지 않은가?

각 관점별로 🔴 반드시 수정 / 🟡 권장 수정으로 분류해줘.
결과를 docs/planning/v1_리뷰.md 파일로 저장해줘.
```

### Step 3. 리뷰 결과를 보고, 이걸 보내세요

```
v1 리뷰의 🔴 항목을 모두 반영해서 v2 기획안을 작성해줘.
🟡 항목 중에서도 타당한 것은 반영해줘.
변경사항을 상단에 요약해줘.
결과를 docs/planning/v2_기획안.md 파일로 저장해줘.
```

**여기까지 하면 1~3단계(기획)가 끝납니다.** 소요 시간: 약 10~20분.

다음 단계는 아래 가이드의 "4단계: 디자인"부터 이어가면 됩니다.

### 💡 빠른 경로 (디자인 건너뛰기)

디자인 없이 바로 코딩하고 싶다면, Step 3 이후에 바로 이걸 보내세요:

```
v2 기획안을 최종 확정하고, 바로 개발 스펙을 논의하자.

핵심 원칙:
- 서버 비용 월 $0 (무료 티어만 사용)
- 가장 빠르게 구현할 수 있는 기술 스택
- 1인 개발 기준

아래 형식으로 정리해줘:
1. 기술 스택 확정 (항목 | 결정 | 이유)
2. 데이터 구조
3. 프로젝트 폴더 구조
4. 구현 순서 (우선순위별)
5. 예상 일정

그리고 바로 첫 번째 구현 항목(프로젝트 셋업 + 데이터 모델)을 시작해줘.
```

이러면 기획 → 개발 스펙 → 구현까지 한 세션에 갈 수 있습니다.

## 이 가이드의 핵심 철학

| 원칙 | 설명 |
|------|------|
| 🪶 가볍게 시작 | 처음부터 완벽한 설계 X → 최소 기능으로 빠르게 시작 |
| 💰 비용 최소화 | 서버리스, 무료 티어 우선. 돈 쓰는 건 사용자가 생긴 후에 |
| 🔄 반복 리뷰 루프 | AI에게 역할을 부여하고, 여러 관점에서 반복 검토 |
| 📄 문서가 곧 코드의 설계도 | AI는 문서를 기반으로 코드를 생성. 문서 품질 = 코드 품질 |
| 🎭 AI에게 역할을 준다 | "시니어 개발자로서 리뷰해줘" → 전문가 관점의 피드백 |

## 전체 프로세스 (9단계)

```
1. 기획 초안 → 2. 기획 리뷰 → 3. 기획 확정
       ↓
4. 디자인 → 5. 디자인 리뷰 → 6. 디자인 확정
       ↓
7. 개발 스펙 논의 → 8. 개발 가이드 작성 → 9. 구현
```

각 단계에서 AI를 어떻게 활용하는지, 어떤 프롬프트를 쓰는지 구체적으로 설명합니다.

## 1단계: 기획 초안 작성

### 목표
앱의 뼈대를 잡는다. 완벽하지 않아도 된다. 핵심만.

### AI 프롬프트 예시

```
나는 [앱 종류] 앱을 만들려고 해.
타겟 유저는 [누구]이고, 핵심 가치는 [한 줄 요약]이야.

아래 항목으로 기획안 초안을 작성해줘:
1. 프로젝트 개요 (비전, 타겟 유저)
2. 핵심 기능 정의 (각 기능별 동작 설명)
3. 화면 구성 (ASCII 와이어프레임으로)
4. 기술 요구사항 (클라이언트, 서버, 데이터 모델)
5. 비기능 요구사항 (성능, 오프라인, 접근성 등)
```

### 작성 팁
- 화면 설계는 ASCII 아트로 충분. 이 단계에서 Figma는 아직 이르다
- 데이터 모델은 테이블 형태로 필드/타입/설명을 명확히
- "향후 업데이트"와 "v1 필수"를 구분해두면 스코프 관리가 쉬움

### 산출물
```
docs/planning/v1_기획안.md
```

## 2단계: 기획 리뷰 (AI 멀티 페르소나 리뷰)

### 목표
혼자 작성한 기획안의 빈 구간을 찾아낸다.

### 핵심 기법: AI에게 여러 역할을 부여해서 리뷰

```
아래 기획안을 리뷰해줘.
다음 3가지 관점에서 각각 피드백을 줘:

1. 사용성(Usability) 전문가로서
   - 사용자 플로우에 불편한 점은?
   - 단계가 너무 많은 기능은?

2. 가시성(Visibility) 전문가로서
   - 중요한 정보가 눈에 잘 띄는가?
   - 시각적 강조가 부족한 부분은?

3. 가독성(Readability) 전문가로서
   - 정보 밀도가 적절한가?
   - 한 화면에 너무 많은 정보를 담고 있지 않은가?

각 관점별로 🔴 반드시 수정 / 🟡 권장 수정으로 분류해줘.

[기획안 전문 붙여넣기 또는 파일 참조]
```

### 리뷰 후 할 일
- 🔴 항목은 반드시 반영
- 🟡 항목은 판단 후 반영 여부 결정
- 수정한 내용을 v2 기획안으로 작성

### 산출물
```
docs/planning/v1_리뷰.md      ← AI 리뷰 결과
docs/planning/v2_기획안.md     ← 피드백 반영본
```

## 3단계: 기획 확정

### 목표
v2 기획안을 최종 검증하고 확정한다.

### AI 프롬프트 예시

```
v1 기획안에서 아래 피드백을 받았고, v2에서 반영했어.
v2 기획안을 보고:
1. v1 피드백이 모두 잘 반영되었는지 확인
2. 새로 발견되는 문제가 있는지 확인
3. 최종 승인 여부를 판단해줘

[v1 리뷰 내용]
[v2 기획안]
```

### 산출물
```
docs/planning/v2_리뷰.md
docs/planning/FINAL_기획안.md   ← 최종 확정본
```

## 4단계: 디자인

### 목표
확정된 기획안을 기반으로 시각 디자인을 만든다.

### 방법 A: Figma + AI (추천)
- Figma에서 직접 디자인
- AI MCP 도구로 Figma 연동 가능 (Kiro, Cursor 등)

### 방법 B: AI로 디자인 생성
```
아래 기획안의 [화면 이름] 화면을 디자인해줘.
- 플랫폼: iOS / Android / Web
- 스타일: 미니멀 / 모던
- 컬러: [브랜드 컬러]
- 참고: 기획안의 ASCII 와이어프레임을 기반으로

SwiftUI / React / Flutter 코드로 바로 구현 가능한 형태로 만들어줘.
```

### 방법 C: 디자인 없이 바로 코드 (초경량)
- 1인 개발이고 속도가 중요하면 디자인 단계를 건너뛰어도 됨
- 기획안의 ASCII 와이어프레임 → 바로 코드 구현
- 나중에 디자인 다듬기

### 산출물
```
Figma 파일 또는 디자인 스크린샷
docs/design/ 폴더에 디자인 관련 문서
```

## 5단계: 디자인 리뷰 (AI 멀티 페르소나 리뷰)

### 목표
디자인의 완성도와 기획 정합성을 검증한다.

### AI 프롬프트 예시

```
아래 디자인을 리뷰해줘. (스크린샷 또는 Figma 링크 첨부)
기획안은 [파일 참조]야.

다음 4가지 관점에서 리뷰해줘:

1. UI/비주얼 전문가 (시니어 8년차)
   - 시각적 완성도, 컬러, 타이포그래피

2. UX/인터랙션 전문가 (시니어 7년차)
   - 사용자 플로우, 터치 타겟, 인터랙션

3. 일관성/접근성 전문가 (미들 4년차)
   - 폰트/라운딩/색상 일관성, WCAG 접근성

4. 기획 정합성 전문가 (미들 3년차)
   - 기획안에 정의된 기능이 디자인에 모두 반영되었는가
   - 기획안에 없는 기능이 추가되지 않았는가

각 관점별로 🔴 Critical / 🟡 Recommended로 분류해줘.
```

### 역방향 피드백 (중요!)
디자인 작업 중 기획에서 빠진 화면/기능을 발견할 수 있다.

```
디자인 작업 중 아래 화면/기능이 기획안에 누락된 것을 발견했어:
[누락 목록]

각 항목에 대해:
1. v1 출시에 필수인지, 다음 버전으로 미룰 수 있는지 판단
2. 필수 항목은 추가 기획안 작성
3. 기존 기획안에 통합
```

### 산출물
```
docs/design/design_review.md        ← 디자인 리뷰 결과
docs/design/design_revision_guide.md ← 수정 가이드
docs/planning/FINAL_기획안.md        ← 추가 기획 반영 (업데이트)
```

## 6단계: 디자인 확정

- 리뷰 피드백 반영 후 최종 디자인 확정
- 필요시 Round 2, Round 3 리뷰 반복
- 확정 후 개발 의뢰서 작성

### 개발 의뢰서 프롬프트

```
아래 기획안과 디자인을 기반으로 개발 의뢰서를 작성해줘.

포함할 내용:
1. 참고 문서 목록 (기획안, 디자인 파일 경로)
2. 화면 목록 (번호, 화면명, 디자인 프레임명)
3. 개발 범위 요약 (클라이언트, 서버, 데이터 모델)
4. 개발팀 구성 제안

[기획안 참조]
[디자인 파일 정보]
```

### 산출물
```
docs/dev/개발의뢰서.md
```

## 7단계: 개발 스펙 논의 (비용 최소화 핵심 단계)

### 목표
어떻게 만들지, 얼마나 가볍게 만들지를 결정한다.

### 💰 비용 최소화 전략 프롬프트

```
아래 개발 의뢰서를 기반으로 개발 스펙을 논의해줘.

핵심 원칙:
- v1은 최소 비용으로 시작. 서버 인프라 비용 월 $0 목표
- 사용자가 늘면 그때 스케일업
- 직접 구현보다 매니지드 서비스/BaaS 우선

아래 역할로 논의해줘:

1. 시니어 개발자 (아키텍처 전문)
   - 기술 스택 선정, 아키텍처 패턴
   - 비용 최적화 방안

2. 서버 개발자
   - 서버리스 vs 자체 서버 비교
   - BaaS(Firebase/Supabase) 활용 방안
   - 무료 티어 범위 분석

논의 결과를 아래 형식으로 정리:
- 기술 스택 확정 (항목 | 결정 | 이유)
- 데이터 구조
- 앱 폴더 구조
```

## 9단계: 구현

### 목표
지금까지 만든 문서를 AI에게 주고 코드를 생성한다.

### 구현 순서 (권장)

```
1. 프로젝트 셋업 (폴더 구조, 의존성)
2. 데이터 모델 정의
3. 핵심 서비스 (인증, DB 연동)
4. 메인 화면 UI
5. 상세 화면 UI
6. 부가 화면 UI (검색, 설정 등)
7. UI 컴포넌트 (토스트, 다이얼로그 등)
8. 통합 테스트 및 버그 수정
```

### AI에게 구현 요청하는 프롬프트

```
아래 문서들을 참고해서 [화면/기능]을 구현해줘.

참고 문서:
- 기획안: [파일 경로]
- 개발 스펙: [파일 경로]
- 텍스트 처리 가이드: [파일 경로]
- 디자인: [Figma 링크 또는 스크린샷]

구현 조건:
- [기술 스택]
- [아키텍처 패턴]
- [코딩 컨벤션]
```

### 구현 중 리뷰 프롬프트

```
방금 구현한 코드를 시니어 개발자 관점에서 리뷰해줘.

확인 포인트:
1. 기획안과 일치하는가
2. 성능 이슈는 없는가
3. 접근성은 충족하는가
4. 에러 처리는 적절한가
5. 코드 컨벤션을 따르는가
6. 순수 함수: 비즈니스 로직이 부수 효과(네트워크/DB/UI)와 분리되어 있는가
7. 모듈화: 파일이 300줄 이하이고, 기능별로 분리되어 있는가
8. 단일 책임: 각 함수/클래스가 하나의 역할만 하는가
9. SOLID: Protocol 기반 추상화, 의존성 주입이 적용되어 있는가
```

### 🏗️ 코드 품질 4원칙 (구현 시 필수)

모든 코드 생성 시 아래 원칙을 지킵니다:

| 원칙 | 핵심 규칙 | 위반 예시 |
|------|----------|----------|
| 순수 함수 | 같은 입력 → 같은 출력. 부수 효과 분리 | 필터링하면서 UI 업데이트 |
| 모듈화 | 기능별 파일 분리. 300줄 이하 | 하나의 파일에 인증+DB+알림 전부 |
| 단일 책임 | 함수 하나 = 일 하나. "and" 금지 | `validateAndSaveAndNotify()` |
| SOLID | Protocol에 의존. 구체 구현 주입 | `let service = FirestoreService()` 직접 생성 |

## 🔄 변경 관리 — "바로 코드 수정" 금지

개발 중이든 완료 후든, 추가/수정/삭제 요청이 들어오면 반드시 프로세스를 태웁니다.

### 왜?
- 문서 없이 코드만 고치면 → 기획안과 코드가 어긋남 → 다음 수정 때 혼란
- 영향 범위 파악 없이 고치면 → 다른 화면/기능이 깨짐
- 문서가 항상 최신이어야 AI가 정확한 코드를 생성할 수 있음

### 변경 프로세스

```
변경 요청 → 1. 분석 → 2. 문서 업데이트 → 3. 코드 수정
            (유형/영향범위)  (기획→디자인→스펙)   (문서 기반)
```

| 변경 유형 | 영향 범위 |
|----------|----------|
| 기능 추가 | 기획 → 디자인 → 스펙 → 코드 |
| 기능 수정 | 기획 → 디자인 → 코드 |
| 기능 삭제 | 기획 → 디자인 → 스펙 → 코드 |
| UI 변경 | 디자인 → 코드 |
| 데이터 변경 | 기획 → 스펙 → 코드 |
| 버그 수정 | 기획 확인 → 코드 (문서가 맞으면 코드만 수정) |

### AI에게 변경 요청하는 프롬프트

```
[변경 내용을 설명]

이 변경사항을 반영해줘.
반드시 아래 순서로 진행해:
1. 영향 범위 분석 (어떤 문서, 어떤 코드가 영향받는지)
2. 관련 문서 업데이트 (기획안, 스펙, 가이드)
3. 문서 업데이트 완료 후 코드 수정
4. 수정 결과 요약
```
